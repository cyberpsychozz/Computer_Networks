# Отчет: Сравнение структуры пакетов IPv4 и IPv6

## 1. Цель работы
Сравнить структуру сетевых пакетов протоколов IPv4 и IPv6 на основе реального дампа сетевого трафика (TCP/IP), захваченного при обращении к Nginx, находящемуся в Docker-контейнере.

## 2. Исходные данные
Захват пакетов производился с помощью утилиты `tcpdump` на порту 8080.
Было выполнено два HTTP GET запроса:
1. По IPv4 адресу: `curl -4 "http://127.0.0.1:8080/parse?url=ros2"`
2. По IPv6 адресу: `curl -6 "http://[::1]:8080/parse?url=ros2"`

### 2.1 Фрагмент захвата протокола IPv4
```text

    127.0.0.1.44124 > 127.0.0.1.8080: Flags [S], cksum 0xfe30 (incorrect -> 0x2d7e), seq 3829954315, win 65495...
```

### 2.2 Фрагмент захвата протокола IPv6

## 3. Сравнительный анализ (по данным дампа)

Из вывода `tcpdump` наглядно видны структурные изменения в заголовках пакетов при переходе от IPv4 к IPv6:

### 3.1. Адресация и идентификатор протокола
*   **IPv4:** Используется маркер `IP`. Адреса мають 32-битный формат (например, `127.0.0.1`).
*   **IPv6:** Используется маркер `IP6`. Адреса имеют 128-битный формат, записанный в шестнадцатеричном виде (в данном случае `::1` — loopback интерфейс).

### 3.2. Жизненный цикл пакета (TTL vs Hop Limit)
*   **IPv4:** Данное поле называется `ttl 64` (Time To Live — время жизни). Исторически задумывалось как время в секундах, но по факту является счетчиком маршрутизаторов.
*   **IPv6:** Поле переименовано в `hlim 64` (Hop Limit — предел прыжков), что устраняет семантическую неточность старого стандарта IPv4.

### 3.3. Управление качеством обслуживания (QoS) и потоками
*   **IPv4:** Присутствует поле `tos 0x0` (Type of Service). Обычный пакет не имеет особых приоритетов.
*   **IPv6:** Внедрено новое поле `flowlabel 0x769a0` (Метка потока). Оно позволяет маршрутизаторам аппаратно идентифицировать пакеты одного потока (в данном случае потока `0x769a0`) для быстрой маршрутизации без необходимости заглядывать внутрь TCP-заголовка.

### 3.4. Фрагментация
*   **IPv4:** В базовом заголовке жестко закреплены поля управления фрагментацией: `id 5632` (Идентификатор), `offset 0` (Смещение) и `flags [DF]` (Флаг Don't Fragment).
*   **IPv6:** В базовом заголовке эти поля **полностью отсутствуют**. В IPv6 маршрутизаторы не фрагментируют пакеты на лету — это обязанность конечного отправителя (выносится в Extension Headers), что существенно ускоряет работу промежуточных узлов.

### 3.5. Определение протокола верхнего уровня (Payload)
*   **IPv4:** Поле `proto TCP (6)` указывает, что инкапсулировано внутри. Размер указывается общим полем `length 60` (весь пакет).
*   **IPv6:** Заменено на поле `next-header TCP (6)`. Размер высчитывается иначе — явно указывается размер данных сразу после заголовка IPv6: `payload length: 40`. Сам заголовок IPv6 имеет строго фиксированную длину (40 байт).

## 4. Вывод

Анализ дампа подтверждает, что заголовок IPv6 был существенно оптимизирован:
1. Заголовок стал фиксированного размера (все необязательные поля перенесены в Next Header).
2. Из базового заголовка убраны затратные для маршрутизаторов механизмы (фрагментация).
3. Введены механизмы быстрой коммутации потоков (`flowlabel`). 
4. Названия полей приведены к их фактической семантике (`TTL` → `Hop Limit`).

Несмотря на ошибку приложения на уровне L7 OSI (HTTP 502 Bad Gateway), протоколы транспортного (TCP) и сетевого (IPv4/IPv6) уровней успешно установили соединение (Three-way handshake) и доставили пакеты до адресата в обоих случаях.
